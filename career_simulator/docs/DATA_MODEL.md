# Модель данных v0.2

SQLite хранит только изменяемое состояние. Статический контент — ранги, события, названия проектов, цены и баланс — находится в `app/content.py`.

## players

Одна строка на Telegram-пользователя.

| Поле | Смысл |
|---|---|
| `telegram_id` | PK, Telegram ID |
| `username` | текущий username |
| `career_day` | номер активного игрового дня |
| `day_key` | ключ последнего дневного сброса |
| `rank` | индекс карьерной ступени 0–5 |
| `track` | `general`, `expert`, `manager` |
| `money` | деньги |
| `skill` | реальный навык |
| `reputation` | доверие к игроку |
| `visibility` | заметность результатов |
| `network` | профессиональные связи |
| `stress` | стресс 0–100 |
| `actions_left` | оставшиеся действия дня |
| `projects_done` | закрытые проекты |
| `projects_failed` | проваленные проекты |
| `promotion_ready` | одобрено ли повышение |

## projects

История проектов игрока. Одновременно активен максимум один.

Связь: `players 1 → N projects`.

Основные поля: `title`, `target`, `progress`, `deadline_day`, награды, статус, день создания и завершения.

## daily_events

Фиксирует одно случайное событие на `player_id + day_key` и сделанный выбор. Это не позволяет перегенерировать событие повторным открытием меню.

Связь: `players 1 → N daily_events`.

## purchases

Фиксирует одно карьерное вложение на `player_id + day_key`. Составной PK одновременно является ограничителем «одна покупка в день».

## action_log

Сырые действия игрока. Нужны не для текущей логики, а для дальнейшего анализа баланса:

- какие кнопки нажимают;
- какие стратегии доминируют;
- где игроки перестают возвращаться;
- какие действия оказываются бесполезными.

## journal

Человекочитаемая история важных событий: старт, новый день, ревью, провал проекта, повышение, событие дня.

## admin_settings

Служебные настройки администраторов.

| Поле | Смысл |
|---|---|
| `telegram_id` | PK, Telegram ID администратора |
| `fast_mode` | включён ли быстрый режим тестирования |

Таблица намеренно не связана внешним ключом с `players`: команда `/reset` должна удалить весь игровой прогресс, но сохранить настройку быстрого режима администратора.

В быстром режиме предыдущие `daily_events` и `purchases` получают архивный `day_key` вида `fast:<career_day>`. Затем запускается штатная логика нового дня. Благодаря этому события и вложения нового тестового дня снова доступны, а история предыдущих дней не теряется.

## Принцип

Не создавать таблицу, пока у неё нет реальной изменяемой сущности. Например, ранги и цены не вынесены в БД: для маленькой игры это только усложнит схему и миграции без пользы.
