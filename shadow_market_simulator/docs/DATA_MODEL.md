# Модель данных SQLite

## Общая схема

```text
shops
 ├── settings
 ├── employees
 ├── candidates
 ├── clients
 ├── supplier_offers ── suppliers
 ├── batches ────────── suppliers + products
 ├── listings ───────── products
 ├── orders ─────────── clients + employees + batches + products
 │    └── disputes
 ├── inbox
 └── ledger
```

Все игровые таблицы привязаны к `player_id`, поэтому один процесс бота может обслуживать несколько независимых магазинов.

## shops

Главное состояние магазина.

Ключевые поля:

- `balance` — денежный остаток;
- `reserve_target` — целевой неприкосновенный резерв;
- `rating` — клиентский рейтинг;
- `employee_reputation` — задел под рынок труда;
- `supplier_reputation` — задел под отношения с поставщиками;
- `last_simulated_at` — точка отсчёта фоновой симуляции;
- `total_revenue`, `total_profit`, `total_orders` — lifetime-счётчики.

## products

Глобальный справочник игровых товаров.

- `base_market_price` — базовая цена единицы;
- `base_demand` — ожидаемый спрос в игровых сутках до модификаторов;
- `complaint_modifier` — склонность категории генерировать обращения.

В MVP используются вымышленные `Neon`, `Amber`, `Echo`.

## suppliers

Глобальный справочник поставщиков.

- `price_modifier`;
- `quality_mean`;
- `quality_sigma`;
- `reliability`.

## supplier_offers

Временные коммерческие предложения для конкретного игрока.

- поставщик;
- товар;
- количество;
- unit cost;
- текстовый сигнал качества;
- срок действия;
- статус.

## batches

Каждая закупка остаётся отдельной сущностью до полного исчерпания.

Это позволяет в дальнейшем строить cohort-анализ по партиям.

- `quantity`;
- `remaining`;
- `unit_cost`;
- скрытое фактическое `quality`;
- поставщик;
- товар.

## listings

Комбинация товара и размера позиции на витрине.

Уникальный ключ:

```text
player_id + product_id + pack_size
```

Цена меняется игроком независимо для каждой фасовки.

## employees

Содержит одновременно видимые операционные поля и скрытые черты.

Видимые по UX:

- alias;
- role;
- pay_per_job;
- deposit;
- has_car;
- jobs_done;
- disputes;
- losses;
- joined_at;
- available.

Скрытые:

- reliability;
- attention;
- honesty;
- loyalty;
- stress (сейчас не показывается напрямую).

`active=0` означает, что сотрудник больше не в команде.

`available=0` при `active=1` означает временную паузу.

## candidates

Кандидат хранит те же скрытые базовые параметры, что будущий сотрудник, но игрок видит только анкету.

После найма значения переносятся в `employees` без повторной генерации. Поэтому решение о найме действительно имеет долгосрочные последствия.

## clients

Наблюдаемая история:

- возраст аккаунта;
- число покупок на площадке;
- покупки в магазине;
- total spend;
- диспуты;
- выигранные диспуты.

Скрытые черты:

- fraud_propensity;
- patience;
- loyalty;
- review_tendency.

## orders

Факт продажи.

Хранит snapshot ключевых экономических величин:

- revenue;
- cost;
- employee_cost;
- quality;
- quantity.

Это важно: последующее изменение цены или партии не переписывает историю заказа.

## disputes

Связан с одним заказом.

- `true_cause` — скрытая истина симуляции;
- `message` — текст претензии;
- `evidence_json` — наблюдаемые признаки;
- `courier_reply` — дополнительное объяснение после запроса;
- `deadline_at`;
- `decision`;
- `status`.

## inbox

Универсальная очередь взаимодействий.

`kind` определяет бизнес-смысл:

- dispute;
- discount_request;
- raise_request;
- leave_request;
- advance_request;
- employee_exit;
- tutorial.

`priority` управляет уведомлениями.

`payload_json` содержит идентификаторы связанных сущностей без создания отдельной таблицы для каждого простого типа сообщения.

## ledger

Не аналитическая прибыль, а журнал денежных движений.

Типы MVP:

- capital;
- sale;
- refund;
- procurement;
- recruitment;
- deposit_in;
- deposit_out;
- employee_loss.

`reference_type` и `reference_id` позволяют связать движение с заказом, сотрудником или предложением.

## settings

Игровые политики конкретного пользователя.

Сейчас хранятся:

- auto_refund_limit;
- auto_partial_limit;
- notifications_enabled;
- hardcore.

Первые два поля пока не выведены в UI: они предназначены для следующего слоя делегирования, где игрок сможет задавать правила автоматическому оператору.

## Почему SQLite достаточно

MVP не использует параллельные высоконагруженные транзакции. WAL включён, внешние ключи включены, соединения короткоживущие. Для одного процесса Telegram-бота SQLite даёт достаточную прозрачность и существенно упрощает отладку симуляции.

Если появятся несколько воркеров, тяжёлая фоновая очередь или веб-панель с одновременной записью, разумной следующей точкой миграции будет PostgreSQL.
