# Витрина и компенсации

## Витрина

UX строится в два уровня:

1. выбор товара;
2. выбор фасовки конкретного товара.

Витрина больше не рассчитывается из общего складского остатка. Продаваемый товар существует только в `retail_positions`, то есть после того, как он прошёл рабочий workflow сотрудников и был опубликован.

Для конкретной фасовки число `поз.` считается как:

```text
available_positions = SUM(retail_positions.position_count)
```

с фильтрами по `player_id + product_id + pack_size` и только по активным розничным сотрудникам.

Объём товара на витрине:

```text
published_units = SUM(position_count × pack_size)
```

Товар, который находится у оптового сотрудника, ожидает передачи или проходит подготовку у розничного сотрудника, в этих цифрах не участвует.

Карточка фасовки показывает:

- текущую цену;
- цену за единицу;
- отклонение от базовой игровой цены;
- общий опубликованный объём товара;
- реальное число готовых позиций этой фасовки;
- inline-кнопки ±5%;
- переход к отзывам о товаре.

Каталог использует `Амфетамин`, `MDMA`, `Кокаин`. Цены и коэффициенты являются внутренними параметрами игрового баланса и не копируют актуальные предложения реальных площадок.

## Связь с сотрудниками

Каждая строка `retail_positions` хранит:

- исходную партию;
- розничного сотрудника;
- товар;
- фасовку;
- количество готовых позиций;
- себестоимость;
- качество.

При продаже позиция списывается именно из этого пула. Поэтому заказ сразу получает конкретного исполнителя и исходную партию, что затем используется в диспутах и отзывах.

## Компенсации по диспутам

Решение разделено на два этапа.

### Этап 1: размер

Игрок выбирает:

- 100% стоимости заказа;
- 50% стоимости заказа;
- отказ.

Отказ закрывает диспут без выбора источника.

### Этап 2: источник

Для компенсации показываются:

- счёт магазина;
- депозит сотрудника, выполнявшего заказ.

Экран показывает доступные суммы. Источник с недостаточным остатком блокируется интерфейсом и повторно валидируется сервисным слоем.

### Списание со счёта магазина

```text
shop.balance -= refund
shop.total_profit -= refund
```

Ledger получает `refund`.

### Списание из депозита сотрудника

```text
shop.balance -= refund
employee.deposit -= refund
employee.losses += refund
```

`total_profit` дополнительно не уменьшается: одновременно сокращаются денежный актив и обязательство перед сотрудником.

Ledger получает `refund_employee_deposit`.

Уменьшение депозита может увеличить непокрытую товарную ответственность сотрудника, поэтому решение по диспуту способно косвенно повысить кадровый риск.

### История

В `disputes` сохраняются:

- `refund_amount`;
- `refund_source` (`shop`, `employee`, `none`);
- `refund_employee_id`.

Аналитика разделяет компенсации магазина и списания из депозитов сотрудников.

## UX-принцип

На каждом шаге есть возврат:

```text
Диспут → Размер компенсации → Источник средств
                       ↑             |
                       └── Назад ────┘
```

Игрок не должен случайно списать деньги одним нажатием из карточки диспута.
