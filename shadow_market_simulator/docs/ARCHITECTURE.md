# NIGHTSHIFT: архитектура

## Runtime

Точка входа — `app/main.py`. При старте приложение:

1. применяет финальные gameplay/UI-патчи;
2. читает `.env` через `app/config.py`;
3. инициализирует SQLite через `app/db.py` и `app/schema.sql`;
4. подключает tutorial- и release-fixes;
5. создаёт `CourierManagementSimulationEngine`, `CourierManagementGameService` и `CourierRecruitmentService`;
6. устанавливает lifecycle входящих и технический analytics log;
7. регистрирует middleware и Telegram-роутеры;
8. запускает фоновый цикл и long polling.

Проект развивался слоями: финальные классы наследуют более общие simulation/game-service уровни, а несколько поздних корректировок интерфейса и обучения устанавливаются явными `apply_*()` функциями. Источником фактической runtime-композиции является `main.py`.

`release_fixes.py` содержит только релизные исправления корректности: актуализацию стартового onboarding, корректное применение накопленного черновика оплаты и защиту одноразовых подтверждающих callback от повторной доставки.

## Карта модулей

### Основа

- `config.py` — переменные окружения.
- `db.py`, `schema.sql` — соединение и основная схема SQLite.
- `simulation.py`, `runtime.py`, `nightshift.py` — базовая симуляция, персональное игровое время и общие таймеры.
- `tutorial.py`, `tutorial_runtime.py`, `tutorial_copy_update.py` — стартовое обучение и его runtime-корректировки.
- `release_fixes.py` — финальные технические safeguards без новых игровых механик.

### Товар и экономика

- `operations.py`, `workflow.py` — ответственность за товар, задачи сотрудников и путь товара до витрины.
- `procurement_market.py`, `gameplay_updates.py` — текущий рынок закупок и финальные параметры каталога/предложений.
- `global_packaging.py` — общий микс фасовок ×1/×2/×5.
- `compensation.py` — общие условия оплаты, начисления и payroll.
- `customer_trust.py` — продажи, оценки, повторные клиенты и доверие магазина.
- `dispute_payments.py` — решения по диспутам и источник компенсации.

### Сотрудники

- `staff_relationships.py`, `staff_insights.py`, `staff_idle.py` — состояние, отношения и наблюдаемая статистика команды.
- `courier_model.py`, `courier_core.py`, `courier_idle.py`, `courier_management.py` — профиль закладчика, рабочие эффекты, отдых, депозитный план и оснащение.
- `recruitment.py`, `courier_recruitment.py` — кампании найма и кандидаты.

### Telegram UI

- `ui_navigation.py` — главное меню и входящие.
- `ui_commerce.py` — `Товар` и `Витрина`.
- `ui_staff.py`, `ui_staff_handlers.py` — команда, склад, передача товара, найм и управление сотрудниками.
- `ui_disputes.py` — диспуты.
- `analytics_handlers.py`, `ui_admin.py` — игровая аналитика и административные команды.
- `ui_common.py` — единое форматирование текста, навигации и кнопок.
- `product_ui_update.py`, `handoff_copy_update.py` — финальные корректировки отдельных экранов и текстов.

### Аналитика

- `business_analytics.py` — игровые отчёты.
- `analytics_log.py` — технический event log действий и ключевых системных событий.

## Границы ответственности

Telegram-роутеры отвечают за навигацию и отображение. Изменяющие состояние операции по возможности проходят через game/recruitment services. Для компактных read-only экранов в UI остаются прямые SQLite-запросы; отдельного ORM/repository слоя нет.

Симуляция изменяет состояние независимо от конкретного экрана: завершает задачи, создаёт продажи, события и сообщения. Поэтому UI перед чтением ряда экранов вызывает `advance()` и не хранит собственное игровое состояние.

Подтверждающие callback, которые по смыслу должны выполниться один раз (`передать товар`, `сменить роль`, `купить следующее улучшение`), дополнительно защищены `OneShotCallbackMiddleware` от повторной доставки того же callback из того же сообщения.

## Транзакции и денежные операции

`Database.connect()` включает foreign keys. Контекст соединения SQLite коммитит успешную операцию и откатывает её при исключении.

Критичные денежные операции выполняются в одном соединении вместе с изменением связанного игрового состояния. Дополнительные idempotency-механизмы используются там, где одно событие может быть обработано повторно:

- закупка атомарно переводит предложение из `open` в промежуточное состояние перед списанием;
- оплата складмена за передачу защищена уникальным `allocation_id` в `wholesale_delivery_payments`;
- закрытый диспут, нанятый кандидат и уволенный сотрудник повторно не проходят проверку активного состояния;
- одноразовые UI-confirm callback защищены middleware.

Депозит сотрудника входит в банковский баланс магазина, но одновременно является обязательством. Поэтому свободные деньги рассчитываются отдельно и не позволяют тратить резерв, депозиты и начисленную зарплату как обычный капитал.

## Фоновый цикл

`main.py` с периодом `SIMULATION_INTERVAL_SECONDS` выполняет:

- `simulation.advance_all()` — продажи, задачи, события и таймеры;
- `recruitment.advance_all()` — завершение поисковых кампаний и формирование кандидатов;
- `game.process_payroll_all()` — суточные выплаты;
- отправку ещё не уведомлённых `important`/`urgent` сообщений из `inbox`.

Основные экраны также вызывают `advance()`, поэтому прогресс не зависит только от фоновой корутины.

Рынок предложений ротируется по реальному времени каждые 15 минут и не масштабируется персональным множителем игрового времени. Один обычный шаг симуляции ограничен 72 игровыми часами, чтобы долгий офлайн не создавал неограниченный объём событий за один проход.

Runtime рассчитан на один asyncio-процесс бота на один SQLite-файл. Несколько процессов с общей БД не являются поддерживаемым deployment-режимом.

## Данные и схема

Основная схема находится в `app/schema.sql`. Часть узкоспециализированных runtime-таблиц, например `tutorial_state`, создаётся соответствующей подсистемой через `CREATE TABLE IF NOT EXISTS`.

Миграционного фреймворка нет. Чистый запуск создаёт всё необходимое без старой БД. Повторная инициализация текущей схемы безопасна, но `CREATE IF NOT EXISTS` не преобразует несовместимую старую структуру таблицы.

## Тесты и CI

`tests/` покрывает симуляцию, закупки, workflow товара, сотрудников, найм, оплату, продажи, оценки, доверие, диспуты, UI и аналитику. Основная команда:

```bash
python -m pytest -q
```

Release-regression тест дополнительно собирает те же gameplay/tutorial/release патчи, что используются при реальном запуске, и проверяет чистый старт и повторные подтверждения. GitHub Actions также запускает компиляцию, ruff, fresh-DB smoke и проверку на возврат удалённых контрактов и документов.
