# NIGHTSHIFT: архитектура v2

## Цель

Архитектура должна позволять добавлять механику без создания очередного `*_update.py`, monkey-patch поверх существующего класса или ещё одного уровня наследования.

Основные требования:

- у каждой механики один канонический источник поведения;
- новые подсистемы добавляются в отдельный пакет, а не новым файлом в корне `app/`;
- Telegram UI не является местом хранения бизнес-правил;
- фоновые процессы вызывают те же сервисы, что и пользовательские действия;
- денежные операции и изменение связанного игрового состояния остаются атомарными;
- idempotency является частью инфраструктуры, а не релизным патчем;
- `main.py` только собирает приложение и запускает polling;
- архитектурные ограничения проверяются тестами и CI.

## Почему текущая структура меняется

Текущий код вырос последовательным наращиванием поведения. Симуляция образует длинную цепочку наследования от `SimulationEngine` до `CourierManagementSimulationEngine`, а game-service — аналогичную цепочку. Поздние изменения дополнительно устанавливаются через `apply_*()` и замену методов/функций во время старта приложения.

Это работает, но имеет три системных недостатка:

1. конечное поведение функции может находиться не в её модуле, а в одном из поздних patch-файлов;
2. удаление или изменение старой логики требует помнить обо всех слоях, которые её оборачивают;
3. новая механика естественным образом провоцирует создание ещё одного наследника или runtime-патча.

Поэтому рефакторинг выполняется не как массовое переименование файлов, а как постепенная замена этих двух способов расширения системы.

## Целевая структура

```text
app/
├── main.py                  # минимальная точка входа
├── bootstrap.py             # сборка зависимостей приложения
│
├── core/                    # инфраструктура без игровых правил
│   ├── config.py
│   ├── database.py
│   ├── clock.py
│   └── schema.sql
│
├── bot/                     # Telegram/runtime infrastructure
│   ├── middleware.py
│   ├── notifications.py
│   └── navigation.py
│
├── commerce/                # закупка, склад, витрина, продажи
│   ├── procurement.py
│   ├── inventory.py
│   ├── storefront.py
│   └── packaging.py
│
├── staff/                   # сотрудники и общие кадровые механики
│   ├── recruitment.py
│   ├── compensation.py
│   ├── relationships.py
│   ├── insights.py
│   └── couriers/
│       ├── model.py
│       ├── performance.py
│       └── management.py
│
├── disputes/                # диспуты и компенсации
│   └── service.py
│
├── tutorial/                # onboarding как самостоятельная подсистема
│   └── service.py
│
├── analytics/               # игровые отчёты и технический event log
│   ├── business.py
│   └── events.py
│
└── ui/                      # экраны/routers; только представление и навигация
    ├── common.py
    ├── commerce.py
    ├── staff.py
    ├── disputes.py
    ├── analytics.py
    └── admin.py
```

Это целевая карта ответственности, а не требование создавать пустые пакеты заранее. Пакет появляется тогда, когда в него переносится реальная каноническая логика.

## Правило зависимости

Допустимое направление зависимостей:

```text
main/bootstrap
      ↓
bot + ui
      ↓
feature services
      ↓
core
```

`core` не импортирует игровые механики или Telegram. Бизнес-логика не импортирует Telegram UI. UI может читать подготовленные сервисами данные и вызывать команды сервисов, но не должен реализовывать альтернативный вариант той же денежной/игровой операции.

Связь между крупными игровыми подсистемами должна идти через публичный API сервиса или небольшую общую функцию. Импорт private-функции другого feature-пакета считается сигналом, что граница выбрана неправильно.

## Композиция вместо бесконечного наследования

Существующая цепочка simulation/game-service сохраняется только на время миграции. Новые механики не должны добавлять ещё один `...SimulationEngine(SomePreviousSimulationEngine)` или `...GameService(SomePreviousGameService)`.

Целевая runtime-композиция состоит из явных сервисов, создаваемых в `bootstrap.py`. Общие операции получают зависимости через конструктор. Для фоновой симуляции используются явные lifecycle hooks (`advance`, `ensure_player`, обработка завершившихся задач), а не подмена методов уже созданного класса.

Небольшое cross-cutting поведение, которое должно участвовать в существующем cooperative MRO во время миграции, оформляется как `*Mixin`, а не как новый «финальный» `GameService` или `SimulationEngine`. Mixin не является самостоятельным runtime-сервисом, не создаётся в `bootstrap.py` и не владеет отдельным состоянием. Он существует как промежуточный миграционный инструмент, пока поведение не будет вынесено в явную композицию сервисов/lifecycle hooks.

Этот подход уже используется для idle-семантики сотрудников, выбора источника компенсации диспута и персонального масштабирования игровых таймеров. После такого преобразования соответствующий класс удаляется из legacy staircase, а архитектурный тест запрещает вернуть его как новый уровень наследования.

До полного переноса старой цепочки она считается legacy-контуром: её можно сокращать, но нельзя удлинять.

## Один источник истины

Запрещён новый код следующих типов:

- `gameplay_updates.py`, `product_ui_update.py`, `*_fixes.py` и аналогичные файлы;
- `apply_*()` для замены функции другого модуля;
- присваивание `other_module.some_function = replacement` как способ установки игровой механики;
- копия renderer/service с почти тем же поведением только ради одной поздней правки;
- новая бизнес-логика непосредственно в callback handler, если операция уже принадлежит сервису.

При изменении поведения исправляется каноническая функция. Если её трудно исправить без patch-файла — это повод сначала изменить границу модуля.

Существующие overlay-модули являются миграционным долгом и удаляются по одному с переносом их финального поведения в канонические подсистемы. Архитектурный тест не позволяет увеличивать их количество.

## Транзакции и idempotency

`Database.connect()` остаётся транзакционной границей для SQLite: успешный контекст коммитится, исключение откатывает изменения.

Правила:

- списание/начисление денег и изменение связанного состояния выполняются в одном соединении;
- повторное подтверждение операции должно быть безопасно на уровне бизнес-операции, если это возможно;
- UI middleware защищает от повторной доставки callback, но не заменяет уникальные ограничения и проверки состояния в БД;
- idempotency middleware живёт в `bot/`, а не в release-fix модуле.

## Tutorial

Tutorial — самостоятельная feature-подсистема, а не набор monkey-patch поверх экранов. Он хранит stage/state и выдаёт UI контекст: подсказку, доступное tutorial-действие и при необходимости модификатор первой гарантированной операции.

Обычный renderer получает этот контекст и отображает его явно. Tutorial не должен во время старта заменять `render_product_root`, `render_team`, analytics-функции или методы game-service.

## Telegram UI

Router/renderer отвечает за:

- разбор callback/message;
- вызов публичной команды сервиса;
- форматирование результата;
- клавиатуру и навигацию.

Он не должен иметь собственную реализацию закупки, выплаты, диспута или передачи товара. Read-only SQL допускается только для действительно простого отображения; если запрос начинает выражать игровое правило, он переносится в feature service/query function.

## Фоновый цикл

Фоновый runtime должен быть вынесен из `main.py`. Он выполняет:

- advance симуляции;
- advance найма;
- payroll;
- доставку важных входящих.

Те же операции должны быть доступны обычному runtime без отдельной «фоновой» версии бизнес-логики.

## Миграционный порядок

1. Зафиксировать архитектурные guardrails в тестах и сделать CI рекурсивным для новых подпакетов.
2. Вынести infrastructure (`core`, `bot`, bootstrap) без изменения механик.
3. Удалить runtime overlay-файлы, перенеся их финальное поведение в канонические функции.
4. Перенести gameplay по feature-пакетам: commerce → staff/couriers → disputes → tutorial → analytics.
5. Заменить длинную цепочку наследования явной композицией сервисов и lifecycle hooks; небольшие промежуточные слои сначала поглощать mixin-ами, не создавая новые уровни staircase.
6. Удалить временные compatibility imports после перевода тестов и UI на новые публичные пути.

Каждый шаг должен оставлять `python -m pytest -q`, `compileall`, ruff и fresh-DB smoke зелёными. Перенос файлов без сохранения поведения не считается завершённым этапом.

## Критерий завершения архитектурного цикла

Рефакторинг завершён, когда:

- в `app/` нет `*_update.py`/`*_fixes.py` и runtime monkey-patching;
- `main.py` не знает деталей отдельных игровых механик;
- новая механика добавляется в существующий feature-пакет или новый самостоятельный пакет;
- simulation/game-service больше не растут новым уровнем наследования на каждую механику;
- у каждой игровой операции есть один канонический implementation path;
- CI рекурсивно проверяет весь `app/`, включая подпакеты;
- чистая БД, существующие игровые цепочки, денежные инварианты и idempotency проходят regression tests.
