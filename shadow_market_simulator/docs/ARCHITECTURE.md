# NIGHTSHIFT: архитектура

## Runtime

Точка входа — `app/main.py`. При старте приложение:

1. читает `.env` через `app/config.py`;
2. инициализирует SQLite через `app/db.py` и `app/schema.sql`;
3. создаёт финальный `CourierManagementSimulationEngine`;
4. создаёт `CourierManagementGameService` и `CourierRecruitmentService`;
5. регистрирует Telegram-роутеры и analytics middleware;
6. запускает фоновый цикл и long polling.

NIGHTSHIFT развивался слоями: специализированные модули расширяют базовую симуляцию и game service наследованием. Новый код должен ориентироваться на финальные объекты, которые создаются в `main.py`, а не на промежуточный класс как на отдельную версию игры.

## Карта модулей

### Основа

- `config.py` — переменные окружения.
- `db.py`, `schema.sql` — соединение и каноническая схема SQLite.
- `simulation.py`, `runtime.py`, `nightshift.py` — базовая симуляция, игровое время и общие таймеры.

### Товар и экономика

- `operations.py`, `workflow.py` — ответственность за товар, задачи сотрудников и путь товара до витрины.
- `procurement_market.py` — рынок закупок и его ротация.
- `global_packaging.py` — общий микс фасовок ×1/×2/×5.
- `compensation.py` — общие условия оплаты и payroll.
- `customer_trust.py` — продажи, оценки, повторные клиенты и доверие магазина.
- `dispute_payments.py` — источник компенсации по диспуту.

### Сотрудники

- `staff_relationships.py`, `staff_insights.py`, `staff_idle.py` — состояние, отношения и наблюдаемая статистика команды.
- `courier_model.py`, `courier_core.py`, `courier_idle.py`, `courier_management.py` — особенности закладчиков, рабочая статистика, отдых, депозитный план и оснащение.
- `recruitment.py`, `courier_recruitment.py` — кампании найма и кандидаты.

### Telegram UI

- `ui_navigation.py` — главное меню и входящие.
- `ui_commerce.py` — `Товар` и `Витрина`.
- `ui_staff.py`, `ui_staff_handlers.py` — команда, склад, передача товара, найм и развитие.
- `ui_disputes.py` — диспуты.
- `analytics_handlers.py`, `ui_admin.py` — аналитика и административные команды.
- `ui_common.py` — общие функции представления и работа с изображениями экранов.

### Аналитика

- `business_analytics.py` — игровые отчёты за 7/30 дней.
- `analytics_log.py` — технический event log действий и ключевых системных событий.

## Границы ответственности

Telegram-роутеры управляют навигацией и отображением. Изменяющие состояние операции должны проходить через game/recruitment services. Для компактных read-only экранов в UI остаются прямые SQLite-запросы; это часть текущей архитектуры и не означает наличие отдельного repository/ORM слоя.

Симуляция изменяет состояние независимо от Telegram-обработчиков. Поэтому экран не должен считать себя единственным местом, где происходят продажи, завершаются задачи или создаются события.

## Фоновый цикл

`main.py` с периодом `SIMULATION_INTERVAL_SECONDS` выполняет для всех игроков:

- продвижение симуляции;
- завершение рекрутинговых кампаний;
- payroll;
- отправку ещё не уведомлённых важных и срочных сообщений из `inbox`.

Основные экраны также вызывают `advance()` перед чтением состояния, поэтому прогресс не зависит только от фоновой корутины.

Рынок предложений живёт отдельно: его ротация привязана к реальному времени и происходит каждые 15 минут независимо от игрового множителя времени.

Один обычный расчёт симуляции ограничен 72 игровыми часами, чтобы долгий офлайн не создавал неограниченный объём событий за один проход.

## Данные

SQLite-файл один на инстанс бота. Каталог товаров и поставщиков общий внутри БД; состояние каждого игрока привязано к `shops.player_id`.

В проекте нет миграционного фреймворка. `db.init()` можно повторять для той же версии схемы, но изменение структуры существующей БД требует отдельного осознанного решения.

## Тесты и CI

`tests/` покрывает симуляцию, закупки, workflow товара, сотрудников, найм, компенсации, продажи, доверие, диспуты, UI и аналитику. Основная команда:

```bash
python -m pytest -q
```

GitHub Actions дополнительно проверяет компиляцию, ruff, запуск на свежей SQLite-базе и наличие удалённых legacy-контрактов.
