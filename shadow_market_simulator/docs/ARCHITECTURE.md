# NIGHTSHIFT: архитектура v2

## Статус

Архитектура v2 введена в `main`. Структурная миграция завершена: runtime overlay-модули и root compatibility-facades удалены, внутренние импорты используют канонические feature-пакеты.

Документ описывает текущие правила архитектуры, а не план будущего переноса.

## Основные принципы

- у каждой механики один канонический источник поведения;
- игровые подсистемы живут в feature-пакетах, а не в новых файлах корня `app/`;
- Telegram UI не хранит альтернативные бизнес-правила;
- фоновые процессы используют те же сервисы и операции, что пользовательские действия;
- денежные операции и связанное изменение игрового состояния выполняются атомарно;
- idempotency является частью инфраструктуры;
- `main.py` — минимальная точка входа;
- сборка зависимостей сосредоточена в `bootstrap.py`;
- архитектурные ограничения проверяются тестами и CI.

## Текущая структура

```text
app/
├── main.py
├── bootstrap.py
│
├── core/                    # конфигурация, БД, базовый GameService, schema.sql
├── engine/                  # базовая симуляция, время игрока, масштабирование таймеров
├── bot/                     # middleware и фоновые уведомления
├── commerce/                # закупка, склад, workflow, фасовки
├── staff/                   # найм, оплата, отношения, инсайты, idle-семантика
│   └── couriers/            # модель, найм и управление курьерами
├── disputes/                # выплаты и источники компенсации по диспутам
├── trust/                   # доверие покупателей, рейтинг, связанные эффекты
├── analytics/               # бизнес-аналитика и event log
├── inbox/                   # lifecycle входящих сообщений
├── tutorial/                # onboarding и гарантии первого игрового цикла
│
├── ui_admin.py
├── ui_commerce.py
├── ui_common.py
├── ui_disputes.py
├── ui_navigation.py
├── ui_staff.py
└── ui_staff_handlers.py
```

Корень `app/` намеренно ограничен assembly/UI-модулями. Архитектурный guardrail запрещает добавлять туда новые доменные модули.

## Направление зависимостей

Базовое направление:

```text
main/bootstrap
      ↓
bot + ui
      ↓
feature services
      ↓
core / engine
```

Правила:

- `core` не должен зависеть от Telegram UI;
- feature service не должен импортировать renderer/callback handler;
- UI вызывает публичные операции сервисов и форматирует результат;
- если read-only SQL в UI начинает выражать игровое правило, запрос переносится в feature service/query function;
- внутренний код использует канонический package-path, старые root import-paths не поддерживаются.

## Канонические feature-пакеты

`core/` владеет конфигурацией, SQLite boundary, канонической схемой и базовым `GameService`.

`engine/` владеет базовой симуляцией и общими семантиками игрового времени/таймеров.

`commerce/` владеет товарным циклом: закупкой, складом, передачами, workflow и фасовками.

`staff/` владеет наймом, оплатой, отношениями и аналитикой сотрудников; courier-specific логика находится в `staff/couriers/`.

`trust/`, `disputes/`, `analytics/`, `inbox/` и `tutorial/` являются самостоятельными feature-пакетами со своим каноническим поведением.

## Наследование и композиция

В проекте ещё существует cooperative MRO-цепочка `SimulationEngine` / `GameService`. Она считается замороженным legacy-контуром: существующие слои можно сокращать или заменять композицией, но новые механики не должны добавлять очередной финальный `...SimulationEngine(PreviousEngine)` или `...GameService(PreviousService)`.

Небольшое cross-cutting поведение допускается оформлять как `*Mixin`, если оно действительно участвует в cooperative MRO и не владеет отдельным runtime-состоянием. Mixin не создаётся отдельно в bootstrap и не является самостоятельным сервисом.

Предпочтительное направление новых изменений — явная композиция сервисов и lifecycle hooks.

## Один источник истины

Запрещены:

- новые `*_update.py`, `*_fixes.py` и похожие поздние overlay-модули;
- `apply_*()` для замены функции или метода другого модуля;
- присваивание `other_module.some_function = replacement` как способ установки механики;
- compatibility-facade в корне `app/` ради поддержки старого внутреннего import-path;
- копия renderer/service с почти тем же поведением ради одной поздней правки;
- бизнес-логика в callback handler, если операция принадлежит feature service.

При изменении поведения исправляется каноническая функция или граница feature-пакета.

Runtime overlay debt равен нулю. Архитектурный тест не допускает его возвращения.

## Транзакции и idempotency

`Database.connect()` является транзакционной границей SQLite: успешный контекст коммитится, исключение откатывает изменения.

Правила:

- списание/начисление денег и изменение связанного состояния выполняются в одной транзакции;
- повторное подтверждение операции должно быть безопасно на уровне бизнес-операции, где это возможно;
- callback middleware защищает от повторной доставки подтверждающих действий, но не заменяет проверки состояния и ограничения в БД;
- idempotency middleware находится в `bot/`, а не в release/runtime patch-файле.

## Tutorial

Onboarding находится в `app/tutorial/`.

`tutorial/core.py` хранит state/stage и tutorial-flow. `tutorial/hooks.py` содержит статически подключённое cross-cutting поведение первого цикла. Tutorial capability включается для production runtime явно через bootstrap и не устанавливает методы/renderer'ы monkey-patch'ами во время старта.

Первый игровой цикл сохраняет свои гарантии: пустой стартовый склад, стартовый капитал, защищённая первая закупка и последовательное обучение основным операциям.

## Telegram UI

Root `ui_*.py` — единственные разрешённые крупные presentation-модули в корне `app/`.

Router/renderer отвечает за:

- разбор callback/message;
- вызов публичной операции сервиса;
- форматирование результата;
- клавиатуру и навигацию.

UI не должен реализовывать собственную версию закупки, выплаты, диспута, передачи товара или расчёта результата сотрудника.

## Runtime и фоновые задачи

`main.py` запускает приложение и polling. Сборка `Database`, simulation/game services, recruitment, analytics, router'ов и middleware находится в `bootstrap.py`.

Фоновая обработка уведомлений вынесена в `bot/notifications.py`. Фоновые действия должны использовать те же канонические операции, что основной runtime.

## Guardrails

`tests/test_architecture_guardrails.py` фиксирует:

- разрешённый набор root `.py` файлов;
- отсутствие runtime overlay-модулей;
- запрет на рост legacy inheritance staircase;
- запрет на присваивание функций/методов в импортированные модули как механизм расширения.

CI рекурсивно проверяет весь `app/` и запускает:

- `compileall`;
- полный pytest suite;
- ruff для ошибок импортов и имён;
- fresh-DB/UI smoke;
- stale NIGHTSHIFT contract/documentation audit.

## Правило дальнейшего развития

Новая механика должна:

1. попасть в существующий feature-пакет или получить отдельный пакет, если это самостоятельный домен;
2. иметь один канонический implementation path;
3. не создавать root facade/overlay;
4. не добавлять новый уровень inheritance staircase без крайней необходимости;
5. сохранять транзакционные и idempotency-инварианты;
6. проходить полный CI на свежей БД.

Архитектурный цикл v2 считается завершённым. Дальнейшая работа — обычное развитие системы в рамках этих правил, а не продолжение структурной миграции.
