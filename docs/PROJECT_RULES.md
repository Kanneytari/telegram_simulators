# Правила репозитория

## Изоляция игр

Каждая игра — самостоятельное приложение. У неё свои:

- `app/` и точка запуска;
- `.env`;
- SQLite-база;
- зависимости;
- тесты;
- документация по специфичным механикам.

Изменения одной игры не должны требовать запуска или БД другой игры.

## Код

- Python-код должен быть простым и читаемым без скрытой магии.
- Telegram-обработчики отвечают за навигацию и представление; игровые правила по возможности живут в сервисах и симуляции.
- Доступ к SQLite должен оставаться предсказуемым: явные запросы и явные транзакционные границы предпочтительнее лишних абстракций.
- Имена модулей, функций и полей должны соответствовать текущим игровым сущностям. Удалённые механики не сохраняются «на всякий случай».
- Комментарии нужны только там, где из кода не очевидна причина решения.

## Данные

В текущих играх используется SQLite3. Схема и правила инициализации принадлежат конкретной игре. Если миграций в игре нет, документация не должна создавать впечатление, что они поддерживаются.

## Конфигурация

Секреты и локальные пути передаются через `.env`; рабочие токены не коммитятся. `.env.example` должен отражать реально читаемые приложением переменные.

## Тестирование

Изменение считается завершённым после запуска релевантного полного набора тестов. Для NIGHTSHIFT дополнительно проверяются компиляция, неиспользуемые импорты, создание свежей БД и отсутствие возвращённых legacy-контрактов.

## Документация

Документация описывает текущее состояние `main`, а не историю разработки и не список будущих идей. Если старая спецификация больше не соответствует коду, её нужно удалить или переписать, а не хранить рядом с актуальной документацией.
